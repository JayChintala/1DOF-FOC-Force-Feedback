CHANGE 1 (plan step B4): TELEM sends the 1 ms mean of Iq, not one raw sample
===========================================================================

WHY
The current loop samples Iq at 16 kHz, but TELEM (sent at 1 kHz) carries one
raw sample and discards the other 15. Measured on the Pi: that sample's noise
is 0.030-0.043 A std at rest, and a 16:1 decimation with no anti-alias filter
folds 500 Hz-8 kHz content into 0-500 Hz (a 247 Hz peak in the spectrum is
probably that). The firmware ALREADY accumulates all 16 samples every period
(IqTelem_UpdateHF / IqTelem_GetMeanAndReset in Src/mc_tasks_foc.c, raw s16A
units) and then throws the mean away. A 16-tap boxcar has nulls exactly at
1, 2, 3 ... kHz, where aliasing folds from. Expected: noise >= 2x lower,
aliased peak gone, ~0.5 ms extra delay at most. The TELEM byte layout does
not change, so the Pi needs no change.

FILE: STM32CubeIDE/Application/User/can_driver.c

(a) After the existing #include lines near the top (mc_parameters.h is already
    included there for scaleParams_M1), add:

    /* B4: TELEM Iq = mean of every 16 kHz sample since the previous TELEM
       (IqTelem_GetMeanAndReset, raw s16A, scaled to Amps). 0 = the old raw
       single sample MC_GetIqdMotor1_F().q. */
    #ifndef TELEM_IQ_MEAN
    #define TELEM_IQ_MEAN 1
    #endif

(b) In static void SendTelemetry(const CAN_TickSample_t* s)  (about line 409):

    DELETE this declaration (about line 413):
      qd_f_t iqd = MC_GetIqdMotor1_F(); /* .q = torque-producing current, .d = 0 in
                                           your control scheme */

    REPLACE the comment block and call (about lines 422-430) that begins
      /* The 16 kHz conditioned-Iq accumulator (IqTelem_UpdateHF) is still
    and ends with
      (void)IqTelem_GetMeanAndReset();
    WITH:

      /* The 16 kHz accumulator (IqTelem_UpdateHF) must be drained exactly once
         per telemetry period -- GetMeanAndReset clears it; left uncalled the
         sum grows without bound and loses float precision. With
         TELEM_IQ_MEAN its mean is what TELEM sends (B4): a 16-tap boxcar has
         nulls at 1, 2, 3 ... kHz, exactly where the 1 kHz decimation of the
         raw sample aliased from. It returns the EWMA if no samples accrued

    #if TELEM_IQ_MEAN

    WITH:

===========================================================================
CHANGE 2 (safety): direct-mode host timeout 200 ms -> 20 ms
===========================================================================

WHY
In direct mode the firmware zeroes Iq if no SET_IQ arrives within
COUPLE_DIRECT_TIMEOUT_US. On the Pi, SD-card write stalls froze the host
control loop for up to 2 s (confirmed). During one such freeze the follower's
last command (-0.07 A) stayed applied for the full 200 ms and the free
follower spun 1.8 revolutions; teleop can command up to 1 A. Every ESC_based
host script resends SET_IQ at least every 10 ms (teleop/spin_test/a5 every
2 ms, plant_gain 1 ms, zero_iq_check 10 ms), so 20 ms does not trip in normal
use; a longer stall now zeroes the current (trip HOST_TIMEOUT) and the next
SET_IQ resumes. HOLD/PEER coupling modes have no host timeout and are not
affected.

FILE: Inc/couple_ctrl.h  (about line 113)

    CHANGE
      #define COUPLE_DIRECT_TIMEOUT_US 200000u
    TO
      #define COUPLE_DIRECT_TIMEOUT_US 20000u /* was 200000u; see FIRMWARE_CHANGES.txt */

    Leave the surrounding #ifndef/#endif and the comment above it as they are,
    except: if that comment states 200 ms anywhere, update it to 20 ms.
    (couple_ctrl.c uses the macro at about lines 265-267; no change there.)

===========================================================================
CHANGE 3 (2026-10-26): average the current-sensor offset calibration longer
===========================================================================

WHY
Measured on the Pi with a slow position sweep of the free leader
(friction_map.py): the leader has an angle-locked torque ripple at 7/rev
(once per electrical cycle) of 36 mA in one START and 24 mA, 13 deg shifted,
in the next. Everything else repeated (28/rev 10.1 vs 10.3 mA, friction
17.1 vs 16.8 mA). An electrical-frequency ripple that changes between STARTs
is the signature of a phase-current offset error: MCSDK re-measures the
offsets on every START (correction 2026-10-26 from the dev review: not via
MCI_StartMotor, but the "already calibrated" IDLE branch in mc_tasks_foc.c
still calls R3_2_CurrentReadingPolarization, which re-measures), and it
averages only NB_CONVERSIONS = 16 samples. With the measured 30-43 mA
per-sample noise that leaves roughly +-10 mA of random offset per phase,
new each START. 8x more samples -> about 2.8x smaller offset error.
It is the largest remaining feel defect on the leader (detents every 51 deg,
bigger than the 20 mA felt dead band), and a host-side map cannot cancel it
because it moves every START.

FILE: Inc/pwm_common.h  (line 37)

    CHANGE
      #define NB_CONVERSIONS 16u
    TO
      #define NB_CONVERSIONS 128u /* was 16u: offset calibration averaging; see FIRMWARE_CHANGES.txt CHANGE 3 */

CONSTRAINTS TO CHECK BEFORE BUILDING (report what you find for each)

(a) THE AVERAGING DIVISOR. The offsets are accumulated and divided in the
    R3_2 current-feedback driver, which is NOT in the git repo (MCSDK is
    git-ignored). The project links it from
      MCSDK_v6.4.2-Full/MotorControl/MCSDK/MCLib/G4xx/Src/r3_2_g4xx_pwm_curr_fdbk.c
    (see STM32CubeIDE/.project). Find where PhaseAOffset / PhaseBOffset /
    PhaseCOffset are summed (the HFCurrentsPolarization* functions) and
    where the sum is turned into the offset (CurrentReadingPolarization /
    the end of calibration).
      - If it divides by NB_CONVERSIONS (or by an expression of it), nothing
        else to change.
      - If it divides by a HARD-CODED shift or constant tied to 16 (e.g.
        ">> 4", ">> 3", "/ 16u", or a shift that assumes 16 samples per
        sector pass), STOP and report the exact lines to the user before
        changing anything. Do not guess the new shift: note that 3-shunt
        polarization may sum each phase over two sector passes, so the
        divisor may be 2*NB_CONVERSIONS.
      - Check the accumulator type: with 128 samples of a left-aligned
        16-bit ADC value (up to 65520) the sum reaches about 8.4e6, which
        needs uint32_t / int32_t (fine), not 16 bits. If it is 16-bit, STOP
        and report.
(b) THE COUNTER TYPE. PolarizationCounter is uint8_t (Src/mc_config.c line
    179, and waitForPolarizationEnd(..., volatile uint8_t *cnt) in
    Src/pwm_common.c). So NB_CONVERSIONS must stay <= 255. 128 is fine; do
    NOT use 256.
(c) THE TIMEOUT. Src/pwm_common.c waitForPolarizationEnd computes
      hMaxPeriodsNumber = (2 * NB_CONVERSIONS) * ((repCnt + 1) >> 1)
    as uint16_t. With 128 that is 256 * ((repCnt + 1) >> 1): check repCnt
    (the TIM1 repetition counter used by R3_2) keeps it below 65535 (it
    will unless repCnt is huge). No change expected.
(d) Search the whole build (Src, Inc, STM32CubeIDE/Application, and the
    linked MCSDK sources) for any other use of NB_CONVERSIONS and report it.

EXPECTED SIDE EFFECT
Offset calibration at START takes 8x longer: roughly 2 x 128 PWM periods at
16 kHz, i.e. about 16 ms instead of 2 ms. The Pi scripts wait for RUN, so
nothing on the Pi changes.

CHANGE 4 (FUTURE -- DO NOT APPLY YET; logged 2026-10-26 at the user's request)
Diagnostic CAN frame: calibrated phase offsets + board temperature, 10 Hz
===========================================================================

WHY
The leader's 7/rev ripple has a fixed phase, grows over time in RUN and
survives a fresh START (TEST_LOG 2026-10-26). Calibration runs with all six
FETs off, while RUN samples mid-period with the low sides conducting.
Reading the offsets and the board NTC back per START, and checking whether
the ripple tracks temperature, separates the two candidate causes: (a) an
offset that exists only while the FETs conduct (calibration cannot see it),
or (b) a thermal offset drift after calibration. The Pi currently works
around the ripple with an adaptive canceller; this change is for root cause.

WHAT (as described by the dev-session review, 2026-10-26; verify before use)
- Offsets: MC_GetPolarizationOffsetsMotor1(PolarizationOffsets_t*)
  (mc_api.c:693-696). Returns false before the first calibration. Fields are
  int32_t but hold averages of left-aligned 16-bit ADC values, so they fit
  in uint16.
- Temperature: NTC_GetAvTemp_C(&TempSensor_M1) (ntc_temperature_sensor.c:197),
  int16 deg C, board NTC, updated in the safety task.
- Frame: 8 bytes [0..1] u16 offA, [2..3] u16 offB, [4..5] u16 offC,
  [6..7] i16 deg C, little-endian like TELEM. ID 0x100 + base + 0x013
  (0x113 / 0x133), outside the node block like DBG; transmit-only.
- ADDED 2026-10-28 (current-measurement breakdown above ~0.5 A, TEST_LOG):
  a second diagnostic frame at 10 Hz (or a faster rate if the TX FIFO
  allows; report what is safe) with FOCVars[M1].Vqd.q and .d (int16 each),
  the PWMC _Super.Sector after the sample-point setup (uint8), and a flag
  for "SECTOR_5 forced this period" (uint8); remaining 2 bytes: the max
  |Vqd| since the last frame (int16). ID e.g. 0x100 + base + 0x014. The dev
  review called Vqd.q "the most useful single measurement": a lasting
  measured-Iq shortfall means the Iq PI output is hitting a limit.
- Send: a SendCalib() from CAN_ControlTick (can_driver.c:514) every 100th
  tick. TX FIFO has 3 elements; TELEM + DBG use 2 per tick, so count drops
  the same way as s_telemTxDropCount.
- Pi side: a parser in ESC_based/software/can_interface.py (Pi session).
- Same hard rules as above: hand edit only, never regenerate.

CHANGE 5 (FUTURE -- DO NOT APPLY YET; logged 2026-10-28 at the user's request;
apply together with CHANGE 4, behind a compile-time switch)
Offset calibration with the bridge SWITCHING at 50 % duty (zero net current)
===========================================================================

WHY (Pi measurements, TEST_LOG 2026-10-28)
The leader's 7/rev torque ripple (an Iq error at the electrical frequency =
a phase-current offset error) grows while in RUN at ~0 A: 8.9 -> 22.3 mA in
89 s; in a 6 min run 18.5 -> 35 -> 50 -> 61 -> 57 mA, fit
17.6 + 47.9 (1 - e^(-t/160 s)) mA, always along the same phase. A fresh
START on a warm board starts at 18.5 mA (cold: 8.9 mA), so re-calibrating
does NOT remove it. Calibration runs with all six FETs off
(R3_2_CurrentReadingPolarization: LL_TIM_CC_DisableChannel CH1/2/3 + MOE,
OSSR), while RUN samples mid-period with the low-side FETs conducting.
Hypothesis (inferred): an offset that exists only while the bridge
switches and grows with board temperature, invisible to an all-off
calibration. Calibrating under the same switching conditions as RUN, with
equal duty on all three phases (no line-line voltage -> ~0 current), would
capture it. CHANGE 4's readback (offsets + NTC per START) tests this:
with CHANGE 5, a warm START should begin near the cold value, not higher.

WHAT (for the dev session to design and REPORT BEFORE EDITING; MCSDK files
are git-ignored, so record every edit exactly)
- In the R3_2 polarization path (r3_2_g4xx_pwm_curr_fdbk.c, around lines
  476-575 and R3_2_HFCurrentsPolarizationAB/C ~1343/~1392), instead of
  disabling CH1/2/3, program all three compare registers to 50 % of the
  period (Half_PWMPeriod/2 in the center-aligned counter, or whatever gives
  equal duty) and enable the outputs, so the bridge switches exactly as in
  RUN at zero voltage vector; keep the ADC trigger at the RUN mid-period
  point. Restore the normal sequence afterwards.
- Behind  #define OFFSET_CALIB_SWITCHING 1  (0 = stock all-off calibration)
  so it can be rolled back without code edits.
- CHECK AND REPORT FIRST:
  (a) Bootstrap: calibration currently happens BEFORE CHARGE_BOOT_CAP.
      With switching, the high-side drivers need charged bootstrap caps;
      decide whether to run CHARGE_BOOT_CAP first (reorder in
      mc_tasks_foc.c IDLE/OFFSET_CALIB/CHARGE_BOOT_CAP) or rely on the
      low-side on-time. Report the safer sequence.
  (b) Shaft must be still: equal duties give ~0 current only without
      back-EMF. START is only sent with the shaft at rest by the Pi
      scripts; note any firmware guard you would add (e.g. skip
      switching calibration if |speed| > small threshold).
  (c) Dead-time: equal on all three legs, so no net current expected;
      confirm nothing (e.g. sector-dependent sampling in
      R3_2_SetADCSampPointPolarization) breaks with outputs enabled.
  (d) Overcurrent/fault paths stay armed during calibration.
- Same hard rules: hand edit, never regenerate; report the diff and build
  result; do not flash until the user says so.

SAFETY: revert the over-current threshold rescaling
===========================================================================

WHY (dev-session review 2026-10-28)
The OCP comparators (COMP1/2/4 vs DAC3, main.c:437-505) compare the OPAMP
INPUTS (PA1/PA7/PB0), i.e. BEFORE the PGA. The "x2 for 8x->16x" rescaling
of DAC_OCP_Threshold (16334, mc_parameters.c:165-168) therefore did not
keep the physical trip current the same -- it RAISED it.

WHAT
Restore DAC_OCP_Threshold to the value that gives the original physical
trip current (the pre-16x value, or recompute from the shunt and the
comparator input network). Report the old value, the new value and the
resulting physical trip current in amps before changing it.
