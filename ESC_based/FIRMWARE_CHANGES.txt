CHANGE 1 (plan step B4): TELEM sends the 1 ms mean of Iq, not one raw sample
===========================================================================

WHY
The current loop samples Iq at 16 kHz, but TELEM (sent at 1 kHz) carries one
raw sample and discards the other 15. Measured on the Pi: that sample's noise
is 0.030-0.043 A std at rest, and a 16:1 decimation with no anti-alias filter
folds 500 Hz-8 kHz content into 0-500 Hz (a 247 Hz peak in the spectrum is
probably that). The firmware ALREADY accumulates all 16 samples every period
(IqTelem_UpdateHF / IqTelem_GetMeanAndReset in Src/mc_tasks_foc.c, raw s16A
units) and then throws the mean away. A 16-tap boxcar has nulls exactly at
1, 2, 3 ... kHz, where aliasing folds from. Expected: noise >= 2x lower,
aliased peak gone, ~0.5 ms extra delay at most. The TELEM byte layout does
not change, so the Pi needs no change.

FILE: STM32CubeIDE/Application/User/can_driver.c

(a) After the existing #include lines near the top (mc_parameters.h is already
    included there for scaleParams_M1), add:

    /* B4: TELEM Iq = mean of every 16 kHz sample since the previous TELEM
       (IqTelem_GetMeanAndReset, raw s16A, scaled to Amps). 0 = the old raw
       single sample MC_GetIqdMotor1_F().q. */
    #ifndef TELEM_IQ_MEAN
    #define TELEM_IQ_MEAN 1
    #endif

(b) In static void SendTelemetry(const CAN_TickSample_t* s)  (about line 409):

    DELETE this declaration (about line 413):

                                           your control scheme */

    and ends with

===========================================================================
CHANGE 2 (safety): direct-mode host timeout 200 ms -> 20 ms
===========================================================================

WHY
In direct mode the firmware zeroes Iq if no SET_IQ arrives within
COUPLE_DIRECT_TIMEOUT_US. On the Pi, SD-card write stalls froze the host
control loop for up to 2 s (confirmed). During one such freeze the follower's
last command (-0.07 A) stayed applied for the full 200 ms and the free
follower spun 1.8 revolutions; teleop can command up to 1 A. Every ESC_based
host script resends SET_IQ at least every 10 ms (teleop/spin_test/a5 every
2 ms, plant_gain 1 ms, zero_iq_check 10 ms), so 20 ms does not trip in normal
use; a longer stall now zeroes the current (trip HOST_TIMEOUT) and the next
SET_IQ resumes. HOLD/PEER coupling modes have no host timeout and are not
affected.

FILE: Inc/couple_ctrl.h  (about line 113)

    CHANGE
      #define COUPLE_DIRECT_TIMEOUT_US 200000u
    TO
      #define COUPLE_DIRECT_TIMEOUT_US 20000u /* was 200000u; see FIRMWARE_CHANGES.txt */

    Leave the surrounding #ifndef/#endif and the comment above it as they are,
    except: if that comment states 200 ms anywhere, update it to 20 ms.
    (couple_ctrl.c uses the macro at about lines 265-267; no change there.)
